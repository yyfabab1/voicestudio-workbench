# voicestudio-workbench · 声音角色工作台（AI 翻唱 / 声音克隆流水线）

> 把一个视频丢进来，自动完成：**抽音轨 → 去伴奏/噪音（UVR5）→ 切片 → 识别文字（ASR）→
> 按声音自动分出不同角色 → 每个角色单独训练**。每个角色出现在网页卡片上，可以试听、
> 改文字、继续训练、让 TA 说话（GPT-SoVITS）或唱歌（RVC）。

一个 Python 进程 + 原生前端：**零前端构建、零前端依赖**，改完刷新就能看。
**34 道回归门禁**串行全绿才算完成 —— 每条判据自带负对照，红不了的判据不算判据。

## 一次导入多个视频（同一个人的素材合成一个模型）

导入框一次可以选好几个视频（Ctrl / Shift 多选，或直接拖一批进来），队列里能
看见选了哪几个、也能单独去掉一个。处理方式有四种：

| 选哪个 | 结果 | 什么时候用 |
|---|---|---|
| **自动认人** | 先按声音分人，再拿**声纹**去库里认「这是哪个已有角色」：认得出就把素材**并进那个角色**，认不出才新建 | **默认**。素材攒到第 N 次之后就用它 —— 不用再手动选「追加到谁」 |
| 按声音自动分 | 多个人自动分成多个角色；同一个人的几段素材会合并到同一角色，**但每次都新建，不会并进已有角色** | 素材库里还是空的、或想每次从零分 |
| 全部合成一个角色 | 这些视频里都是同一个人，强行并成一个 | 多个视频同一个人，且明确知道库里没有他 |
| 每个视频各自一个角色 | 一个视频一个角色 | 每个视频是不同的人 |

**自动认人怎么判的**（细节见下面「加素材时自动认人」一节）：
给每个已有角色存一个**声纹中心向量**（就是整合包里做说话人验证的那个 eres2net），
新素材切成段之后，**每一段**去比各角色的中心，取这些距离的**中位数**；
中位数小于门槛而且**唯一最像**，才认成那个角色。

**给已有角色继续加料**（手动指定，不用等它猜）：角色详情页的 **＋ 追加素材（新视频）**。
这是「素材可以一直攒」的入口——第一次导入只是起点，后面看到他新的视频就再拖进来，片段只增不减：

- 新片段**拷进同一个 `slices/`**，切片名带 `v0_` / `v1_` 前缀（第几个源），
  两个文件里同名的片段不会互相覆盖。
- **人工校对过的文本不会被 ASR 冲掉**：已在库里的同名片段保留老的那一条记录。
- 同一份素材追加两遍**不会翻倍**（按切片名去重）。
- 追加完不会新建角色，`result_roles` 还是原来那一个。

## 加素材时自动认人（不用再手动选「并到谁」）

素材攒到第二、第三次之后，真正烦的已经不是"怎么分人"，而是"**这是库里哪个角色**"。
以前只有两条路：每次都新建一个角色（同一个人散成好几个），或者手动去界面上选一个
「追加到 XX」。这一版补了第三条：导入方式选 **自动认人**（默认），它会自己判断。

**怎么判的**：

1. 给每个已有角色存一个**声纹中心向量**。用的是整合包自带、做说话人验证的那个
   eres2net（`GPT_SoVITS/sv.py` 的 `ERes2NetV2`）。第一次导入的新角色会顺手算一个，
   以前导入的老角色在第一次用「自动认人」时**自动补算**（缓存在角色记录里，只算一次）。
2. 新素材切完段，**每一段**去比每个角色的中心，取这些距离的**中位数**当"像不像"。
3. 中位数 ≤ 阈值、而且它是**最近的**那一个 ⇒ 并进这个角色（追加，不新建）；
   否则 ⇒ 新建角色。

**为什么用"逐段比、取中位数"，而不是"两个中心直接比"**：中心对中心量的主要是
"每侧有多少段"（抽样噪声），不是"是不是同一个人"。实测同一个角色切四份，中心距离
能到 0.131；随机分半只有 0.004 —— 差两个数量级，而"异人"侧直接把区间压在中间、完全重叠。
换成逐段取中位数之后，段少也不会把中心带跑，少数分错的段也挪不动中位数。

**用哪一份声纹向量（量出来的，不是拍的）**：feat_cli 一次存两份 ——
`emb`（`compute_embedding3`，走 `forward3`，20480 维的**时间平均融合特征**，GPT-SoVITS
拿它做别的用途）和 `sv`（模型自带的说话人嵌入头 `forward`，**192 维**）。实测 40 正 / 40 负：

| 阈值 | `emb` 收进率 / 误收率 | `sv` 收进率 / 误收率 |
|---|---|---|
| 0.20 | 68% / 0% | 70% / 0% |
| 0.22 | 88% / **2%** | 85% / 0% |
| 0.23 | 88% / **10%** | 92% / 0% |
| 0.25 | 98% / **15%** | 92% / **8%** |

⇒ `emb` 的「零误收安全带」只有 0.20~0.21（宽 0.01），一放宽立刻漏；`sv` 的安全带是
0.20~0.24（宽 0.04），同一档上收进率还更高。所以用 `sv`。
还试过「两个向量 AND 投票（两道闸都放行才并）」：**没有收益** —— 异人侧两道闸拦的是
同一批样本（"只有 emb 拦下" 0 个、"只有 sv 拦下" 0 个），AND 只会被弱的那道拖住，
同人收进率从 92% 掉到 78%，误收没更少 ⇒ 单路 `sv`。
附带的实惠：192 维 vs 20480 维 —— 角色声纹缓存小 100 倍、比对快 100 倍。

**⚠ 真正的坑是"薄中心"（这一条是被一条红得有道理的判据逼出来的）**：一开始基准角色的
中心只用 **17 段**算出来，结果别人的素材到它只有 **0.2103**，低于当时的阈值 0.23 ⇒
库里要是没有那个人自己的角色卡，这段素材就会被并进来。一开始我猜是"中心太糊、什么都
离它近"，被实测**否掉**（同人自比几乎不随段数变）。真正的原因是"异人"侧的**左尾**被压低。
40 次抽样量出来：

| 中心用 k 段 | 同人 p95（越高越危险） | 异人 p25（越低越危险） | 异人 p10 |
|---|---|---|---|
| 8 | **0.3151** | 0.2517 | 0.1976 |
| 12 / 17 / 22 | ~0.198 | 0.2496~0.2579 | **0.2266~0.2404** |
| **30 / 45 / 60 / 120** | **0.180~0.190** | **0.2614~0.2684** | 0.2379~0.2521 |

⇒ 段数 < 30 时异人 p10 落到 0.2266~0.2404（低于 0.23 ⇒ 会误收）；
≥30 段时异人 p25 稳定在 0.26 以上、同人 p95 在 0.19 以下，**余量 0.07**。
（★ 量这一条时每档必须抽够 40 次：只抽 8 次时 p10 取到的是**最小值**，结果在
0.198~0.272 之间乱跳，看着像"没规律"，其实是样本不够。）

所以最后是**两条规则**：

- **`MIN_CENTER_SEGS = 30`**：中心段数不足 30 的角色**不作为认人候选**（素材攒够了
  自己会变"实心"，不用手动管）；
- **`MATCH_DIST = 0.21`**：在 ≥30 段中心的前提下，同人 p95 0.19 < **0.21** < 异人 p25 0.26。

**取向定死：宁可认不出，也不许错并。** 认不出只是多建一个角色（用户手动一并就好），
错并是**静默污染训练集**。所以：新素材段数 < 6 不认；中心不足 30 段的角色不当候选；
维度对不上不认；换了向量种类时老缓存自动失效重算（`voice.kind` 版本标记）—— 不然
老中心会一直被"静默跳过"，表现成"这个角色永远认不出"而且不报错。

**⚠ 这条功能的证据边界（如实说）**：用来校准的"异人"侧只有**一个**别的说话人
（另一个视频里的人声）。所以"误收 0%"只能说是**在这一个人身上没漏**，不等于在
所有人身上都不漏。真遇到声音很像的两个角色，最后一道保险还是它的取向（认不出就新建）。

## 段级纯净度：不属于这个声音的段，自动挑出去

上面那层是**整堆**认人（取中位数）。它有个盲区：一堆里混进别人的**整段**时，中位数
照样过阈值 ⇒ 那些段被一并并进去。任务照样完成、角色段数还变多了，只有训练集被
静默污染，等训出来声音不对才发现，十几分钟机时已经烧掉。

所以认人之后还有一层 **段级复核**：一堆认成某人之后，**每一段**再单独判一次。

| 这一段的情况 | 处置 |
|---|---|
| 离某个角色 ≤ `SEG_MATCH_DIST`（0.30） | 归它 —— 如果别的角色更近就**改判过去**，不留在原堆 |
| 谁都不像，但这堆被认成了某人 | **剔出去**，放进「待归类的片段」（不丢，随时能归位） |
| 谁都不像，这堆本来就要新建角色 | 留在新建的角色里（它本来就是个新的人） |
| 太短（< 2 秒），声纹不可信 | 按簇级结果走，这一层不乱动 |

**没认出来、要新建角色的那一堆**没有角色中心可对照，改用 `purge_outliers`：拿这一堆
自己的中心当尺子，中位数 + MAD 挑离群段。★ 这里必须带**绝对下限**
（`OUTLIER_FLOOR = 0.30`）—— 实测纯净堆上没有它会被砍掉 **4.2%**（正常尾巴被当成离群），
加上之后归零。

**★ 问题到底在哪一层（先量了才动手，没照直觉改）**：

| 对照（半段 2.5s 口径，p50） | 距离 |
|---|---|
| 同一个人换句话（人造拼接） | 0.313 |
| 换了一个人（人造拼接） | 0.614 |
| **真实切片自己的前半 vs 后半** | **0.232** |

真实段内比"同一个人换句话"还小 ⇒ **段内本来就没什么混音**。所以"把段切得更碎"是
错的：会把整句切烂，还捞不出东西。真问题在**段与段之间**，判据因此落在整段这一层。

**阈值是跨批标定的，不是自比**（第一版就错在这儿，被门禁当场抓出来）：第一版拿
同一批切片算中心、又拿这同一批去比 ⇒ 同人 p95 只有 0.134，阈值定成 0.25，
端到端一试 **20 段同人素材被剔掉 2 段（10%）**。改成跨批（A 批 60 段算中心、
B 批**另外** 60 段当新素材，两批不重叠）重量：

| 口径 | p50 | p90 | p95 | 关键分位 |
|---|---|---|---|---|
| 跨批同人 | 0.092 | 0.142 | 0.182 | **max = 0.253** |
| 异人 | — | — | — | **p05 = 0.374** |

阈值扫描：0.25 → 误杀同人 1.7%；**0.28 / 0.30 / 0.32 / 0.35 → 误杀 0% 且漏放 0%**；
0.38 → 开始漏放异人 5.4%。⇒ 取 **0.30**（同人 max 0.253 与异人 p05 0.374 的中点，
两头各留约 0.07 余量）。

⚠ `MATCH_DIST = 0.21` 比这个值**小**不是写反了：簇级取的是一堆段的**中位数**
（稳定、分布窄），段级是**单个段**（噪声大、分布宽得多）。同一个人在两层上的
水位本来就不同，别拿一个数去套另一层。

**剔出去的段不会消失** —— 一律进「待归类的片段」角色，界面上看得到、能手动归位。
导入日志会给自检报告：归位几段、改判几段、剔除几段、几段因太短没参与。

## 训练质量档位

| 模型 | 档位 | 说明 |
|---|---|---|
| 说话 GPT-SoVITS | 快速 15 / **标准 30** / 完美 60 轮 | 越多越像，过头会崩 |
| 唱歌 RVC | 快速 50 / **标准 150** / 完美 300 轮 | 少了会沙哑，宁可多训 |

### 300 不是上限：可以自定义任意轮数

每个训练面板和翻唱台都有一个「**自定义**」档位，选中后旁边会出现轮数输入框：

| 模型 | 上限 | 为什么 |
|---|---|---|
| 说话 GPT-SoVITS | **200** | 再往上容易过拟合，合成开始发疯（体检也拦不住的那种）。所以 60 档之上还有余量，但不该鼓励 |
| 唱歌 RVC | **5000** | RVC 轮数少会沙哑，**越多越稳**。RVC 官方默认就是 20000 轮，300 只是个推荐值不是天花板 |

填超上限会被自动收进上限并在日志里说明。**训练两次不是叠加**：
每次训练都是**用当前素材从头再训**（GPT-SoVITS 的续训 checkpoint 在
torch 2.6+ 下加载不了，见下「已知边界」），所以第二次训 600 轮得到的是
600 轮的新模型，而不是接着上一次继续。RVC 相反：`train/train.py` 自带
从 `logs/<exp>/G_*.pth` 续训的逻辑，所以**同一份素材连着训两次是可以的**，
第二次会接着上次的轮数往下走。

**训完自动出声体检**：真合成一句话过判据才采用，不合格自动降回更早的权重（最多试 4 个）。
体检通过的那句会留作「体检样本」，训练完立刻能听。

### 继续训练：界面直接告诉你「已经训到第几轮」

唱歌（RVC）能接着上一次往下训，**前提是这次的目标轮数要大于已经训过的轮数**
（`-te N` 的语义是「训到第 N 轮」，不是「再训 N 轮」）。所以训练面板和翻唱台
都会显示「已训到 N 轮」，并且在你填的目标轮数 ≤ N 时：

- **当场标红**，并写明该怎么办；
- 点训练**直接被拦下，一个任务都不提交**；
- 自动把档位切到「自定义」并填上一个能续训的值（`max(2N, N+50)`）。

以前这里没有闸门：要等训练起了进程、跑完预处理才报错，用户白等几分钟还不知道为什么。

已训轮数是从 `logs/<实验名>/G_*.pth` 里读出来的（`stages/rvc_state.py` 读 checkpoint
的 `iteration` 字段 —— **文件名读不出轮数**，`-l 1` 时文件名固定是 `G_2333333.pth`），
按文件 mtime 缓存，界面每问一次不会真去开一次 torch 进程。
接口：`GET /api/role/<id>/rvc_state` → `{"epochs": N, "exp": "<实验名>"}`。

**说话模型（GPT-SoVITS）不吃「续训」这一套**：它每次都是拿当前素材从头重训，
填多少训多少，所以那栏写的就是「开始训练（用当前素材重训一遍）」。

导入视频的那个框里也有同一套「自定义…」轮数输入（上限 200），
与角色页训练走**同一个上限收口**——两个入口两种口径等于上限形同虚设。

### 训完绑定的是哪一个权重（踩过的坑）

RVC 每次到保存间隔存一份 `<实验名>_e<轮数>_s<步数>.pth`，**训完再单独存一份不带轮数的
`<实验名>.pth`** —— 那份才是真正的最终权重（`process_ckpt.py` 的 `savee()` 用实验名
直接命名）。所以选权重必须：

1. 优先用不带轮数的最终权重；
2. 只有在没有最终权重时，才在带轮数的那批里**按轮数数值取最大**。

早先这里是 `sorted(...)[-1]`（按文件名字典序），而字典序里
`"e150" < "e90"`、`"e300" < "e90"` —— 于是训满 300 轮，绑定的却是 90 轮那份。
`pick_rvc_weight()` 修掉了它，`roles.json` 里已有的记录也已重新绑定。

**索引库同理**：判断「这个模型有没有特征索引」不能拼 `<模型名>.index`，
索引真名是 `<实验名>_added_IVF<n>_Flat_nprobe_1_<实验名>_v1.index`，
而且模型名带 `_e150_s1200` 这种尾巴，两边根本对不上。现在统一走
`_find_rvc_index()`，与 RVC 自己 `infer/vc/utils.py` 的匹配规则一致
（去掉轮数后缀、跳过 `trained` 合并索引、接受 `_added_` / `_v1` / `_v2`）。

## 唱歌链路：先分离，再变声，最后用伴奏混音

**这是「唱出来没法听」的根治点，而且是流程级的错，不是参数调优能救的。**

以前的做法是「整首歌 → RVC → 再和原曲混合」，两个硬伤：

| 硬伤 | 后果 |
|---|---|
| 整首歌（含鼓、贝斯、和声）直接喂给 RVC | RVC 是「人声→人声」的模型，靠 f0 曲线工作，它会给鼓点也编一条 f0，输出跟着节奏乱跑 |
| 混音时用**原曲**当伴奏 | 原曲里带着**原唱**，混出来就是原唱 + 角色两个人在唱 |

实测（`data/roles/r8c323d43/final/` 那两条成品，同取第 68~98 秒）：

| 指标 | 旧链路 | 新链路 |
|---|---|---|
| `corr(成品 − 伴奏, 原唱人声)` | **+0.515** | **−0.009** |
| `corr(原曲, 成品)` | +0.863 | −0.148 |
| 成品里的人声响度 RMS | 0.119 | 0.219 |

旧链路成品里有一半是原唱；新链路 **−0.009，等于完全没有原唱**。

现在的顺序固定为四步（每一步都有步骤条）：

```
① 分离人声与伴奏   原曲 →(UVR5)→ vocal.wav + inst.wav（结果按「原曲+分离模型」缓存）
② 估算音高（自动） RMVPE 量原唱与角色音域，给出该升降几个半音
③ 歌声转换（RVC）  只对 vocal.wav 变声
④ 混合成品         inst.wav + 角色人声，响度对齐 + 平滑噪声门 + 防削波
```

- **分离器不再写死，是「先比再选」**（见下一节）。候选：Roformer
  （`model_bs_roformer_ep_317_sdr_12.9755`，SDR 12.98）/ `HP5_only_main_vocal` /
  `HP2_all_vocals`。先切中间 30 秒让每个候选各跑一遍打分，分最高的跑全曲；
  漏伴奏超过阈值再分一次，第二次更好才用它。全部失败才按顺序兜底 —— 不让它把链带死。
- **缓存**在 `data/cache/sep/<键>/`，键 = 原曲路径 + 大小 + mtime + **选优策略版本**
  （★ 不带模型名：模型是比出来的，不是写死的）。命中缓存时会告诉你上次选的是谁、
  多少分。改一个参数重跑时分离直接复用（分离 4 分钟的歌要 48 秒）。
- **混合脚本** `stages/mix_cli.py` 按 RMS 自动对齐（伴奏 0.12 / 人声 0.18 / 成品 0.13），
  带 20ms 滑动 RMS 的平滑噪声门（压掉 RVC 在间奏留下的底噪），峰值封顶 0.95。

### 分离自动选优：不再「跑通就算好」

以前分离是「默认 Roformer，跑不通退 HP5」，两个问题：**没人知道分得好不好**，
而且**导入链和唱歌链的口径不一致**（训练出来的模型因此会飘）。

现在先给分离质量造一把尺子（`stages/sep_eval.py`，只看 numpy/soundfile，不加载 torch）：

| 指标 | 量的是什么 | 为什么这么定 |
|---|---|---|
| `leak` | 人声轨 vs 伴奏轨逐帧幅度谱相关的**中位数** | 漏进来的伴奏越多越高。权重最大（0.55） |
| `floor_db` | 能量包络 10 分位 − 90 分位 | **区间型**，不是越低越好：实测最安静的那个模型（−98dB）真值 SDR 反而最差（3.40），因为它把人声也削掉了 |
| `hf_ratio` | 6k 以上能量占比 | 伴奏漏进来时高频结构会跟着变 |
| `body` | 人声 RMS / 原曲 RMS | 只做**乘性闸门**（`×(0.2+0.8·body)`）。加性时"削过头"能拿 66.7 分、比干净版 61.5 还高 |

尺子本身是真的验过的（`verify_sep.py`，12 项）：

- 用**合成真值**校准（把分好的 (vocal, inst) 按不同 SNR 重混 ⇒ 真值已知 ⇒ 算真 SDR）：
  真值 SDR **9.21 / 5.49 / 3.40** 对应评分 **96.4 / 81.4 / 72.0**，**同序**；
- 真跑一遍分离器：真值 SDR **21.2 dB**，评分 77.0；而「没分离」只有 20.9 分、
  「漏 60% 伴奏」只有 4.4 分 —— 三种坏法都被压在下面。

选出来的结果写进 `data/cache/sep/<键>/meta.json`（选了谁、多少分、各候选的明细），
并且**跨所有歌累计** `data/sep_pick_stats.json`：平均分高的模型下次先试，省显卡。
这是跨歌的统计，**不是给某一首歌调参**。

### 非歌声段保护：口哨 / 间奏再也不许被「唱」出来

**RVC 只认 f0 曲线，它分不出「人在唱」和「人在吹口哨」。** 分离后的人声轨里，口哨段
是一条极高、极纯的持续音（实测：f0 662 Hz、谱平坦度 **0.0013**，而同一首歌的正常歌唱段
是 f0 262 Hz、平坦度 0.19，差一个数量级）。RVC 会照样用角色的嗓音把那个音"唱"出来：

| 同一段 19 秒（角色 = 男声） | 输出 f0 中位 | 输出/输入 RMS |
|---|---|---|
| 正常歌唱段 | 87 Hz（= 262 降 19 半音 ✓） | 正常 |
| 口哨段 | 220 Hz（= 662 降 19 半音，数学也对，但那是**高两个八度**） | **2.97 倍**，平坦度 0.013 → 0.245 |

对男声角色来说，220 Hz 的持续音就是用假声在吼 —— 这就是"每到吹口哨就吼"。
**调 RVC 参数救不了这件事**，因为参数改不了"口哨不是唱"。

做法（`stages/nonvocal_guard.py`）：用**谱平坦度**当主判据（低频靠、窄带 = 纯音），
f0 当辅助，逐帧判「非歌声」，然后把 RVC 输出里对应的段**换回原始人声轨**
（口哨不承载角色音色，保留原声是翻唱里的常规做法），边界 20ms 交叉淡化。
判据：平坦度 < 0.05（口哨/纯音 0.001~0.03，正常歌唱 0.15~0.30，而清辅音/气声是
宽带噪声、平坦度接近 1，**不会被误伤**）；单段至少 15 帧（0.15 秒）；
相邻段间隔 < 0.5 秒并成一段（口哨是由一串音符组成的，切碎会让听感反复横跳）。

三种模式（翻唱台改词区有下拉）：`keep`（默认，口哨还在、只是不再被吼）/ `mute`
（不要口哨就静音）/ `off`（完全等于旧行为）。

**踩过的坑：`loud` 门槛的循环依赖。** 一开始用"高于全曲 RMS 的 25 分位"筛掉没声音的帧，
可是**非歌声段自己占比一高，这个分位数就落在非歌声段身上** —— 于是那一段里偏轻的一半
帧被判成"没声音、不算"，剩下的是些不足 15 帧的碎片，全被最短段过滤掉 ⇒ **一段都判不出来**。
合成素材「唱 3 秒 – 口哨 2 秒 – 唱 3 秒」因此判 0 段。改成相对**峰值**的小门槛
`max(0.005, 0.02 × p95(rms))`：它只排掉真正的静音（间奏、留白），与"非歌声段占多少比例"无关。

真实整曲回归（一首 224.9 秒的歌，`mode=keep`）：判出 **39 段 / 33.23 秒**非歌声段，
全曲谱平坦度中位 0.124（正常歌唱区间）。修 `loud` 门槛时专门做过新旧版并排对比：
在两者都有效的重叠窗口内判出的段**完全相同**（8 段一一对应），没有出现"新版放宽门槛、
把歌唱段也保护起来"的误伤。门禁 `verify_nonvocal.py`（9 项）完全自足：自己合成
「唱 3s | 口哨 2s | 唱 3s」，RVC 侧用"把口哨也当唱了"的坏版本模拟（降 19 半音的谐波 +
放大到 0.9），并带一条负对照「全曲都是唱 → 必须判 0 段」。

### 视频可以直接当歌用

把 mp4/mkv/mov 等视频拖到「歌」槽，会**当场用 ffmpeg 把音轨抽出来**
（统一成 44.1kHz 立体声 wav），后面分离/变声/混音走的还是同一条链。
抽不出来（比如这个视频根本没有音频流）会明说原因，而不是给你一个废文件。
实测：8.9MB 的 mp4 → 316.5 秒音轨。

## 唱歌输出两条轨（分开存）

- `mix_*.wav` 成品（角色人声 + **分离出来的伴奏**），能直接听能发
- `voice_*.wav` 人声干声，方便重新编曲/混音/进 DAW
- `mix_preview_latest.wav` / `voice_preview_latest.wav` 试听小样（固定名，只保留一份）
- `*.lrc` **歌词**，跟成品同名、放在同一个目录（播放器直接认）

### 成品带歌词

成品记录里存一份歌词（`lyric`），卡片上有「歌词」按钮展开看、能复制，旁边能下 `.lrc`。
歌词取的是**实际唱的那版词**：改过词就是新词（存原词等于存错，过几天再想改一版会对不上）。

两条不做的事，都是踩过或者想清楚会踩的：

- **不在唱歌流程里自动跑语音识别**。那个识别模型第一次要下 1.5GB，用户只是想唱首歌，
  不该被拖着等一个 G 多的下载。所以：这首歌**之前识别过**（有缓存）就顺手带上；
  没识别过就在成品上留一个「识别歌词」按钮，他自己点，点了才跑、有进度条。
- **不按行数均分时间轴**。句数跟识别到的时间戳对不上时，宁可给一份不带时间轴的纯文本
  歌词，也不按总时长/行数硬分 —— 均分出来的时间轴看着像真的，其实一句都对不上，
  播放器照着错的时间滚，用户会以为是识别坏了。

## 参考项目怎么用的（取长补短）

你给的那些项目，能直接搬到本机（有 GPU、有 ffmpeg、有 Python）的都搬了；
**必须跑在浏览器里的方案（WASM / WebGPU）本机不采用** —— 本项目是本地显卡干活，
在浏览器里再跑一遍分离/变声，几百 MB 的模型下载 + 无 GPU 加速，只会更慢更差。

| 环节 | 参考 | 本项目怎么做的 |
|---|---|---|
| 视频→音频 | ffmpeg.wasm / Mediabunny / frameflow | **直接用本机 ffmpeg**：视频丢进「歌」槽时**当场抽音轨**（`-vn` + 44.1k 立体声）。实测 8.9MB 的 mp4 抽出 316 秒音轨 |
| 人声分离 | demucs-onnx / bs-roformer-web / htdemucs-6s | 服务端跑 **BS-Roformer**（SDR 12.98），失败自动回退 VR HP5；结果按「原曲+模型」缓存 |
| 变调/变速 | signalsmith-stretch / bungee / SoundTouchJS | 试听台用浏览器内置 `playbackRate` + `preservesPitch`（慢放不变调），零依赖 |
| 实时音高检测 / 跟唱评分 | mic-pitch / nightingale / ultrastar-score | **成品客观质检**：用 RVC 自带的 RMVPE（和推理链同一把尺子）逐帧比原唱与角色的 f0，量音准吻合率 / 起伏比 / 对齐 |
| 多轨时间线 | waveform-playlist / AudioMass / WAM-Studio | 成品卡片上的**多轨试听台**：分轨切换 + A/B 交叉淡化 + 变速慢放 + 质检徽章 |
| 音色转换 | OpenVoiceChanger / Timeline Studio OpenVoice V2 | 仍是 **RVC**（本项目已有训练链路）；关键补上了**底模**（见下一节） |
| 音频降噪 | wasm-audio-ferrite | 混音脚本里的**平滑噪声门**（20ms 滑动 RMS + 9dB 软膝）压掉 RVC 在间奏留的底噪 |
| 歌声合成 | WebUtau / VocalRender | 不适用 —— 本项目是「让已有角色翻唱」，不是从乐谱合成 |

浏览器端方案没采用的原因如实说：它们是**无 GPU 环境下的正确选择**，
而本机有 RTX 5070，服务端跑大模型比在浏览器里跑 WASM 快一个数量级，
也不必让用户下几百 MB 的 ONNX。

## RVC 底模：不装它，歌声模型根本学不会「跟着旋律唱」

**这是「唱出来的歌没法听」最主要的原因，而且它坏得一点声音都没有。**

RVC 的训练参数 `-pg`（生成器底模）/ `-pd`（判别器底模）默认是空字符串。
**不传就是从随机初始化开始训**，而不是从官方那个在海量多说话人数据上预训练过的
底模继续练。从零训出来的模型**学不会跟着旋律唱**，它只会模仿训练素材的平均音色：

| 症状 | 实测（本机 r8c323d43，66 条素材 / 300 轮 / 无底模） |
|---|---|
| 输出死死卡在角色自己的音区 | 原唱人声中位 **268 Hz**，角色输出中位 **106 Hz** |
| `--pitch` 完全无效 | 从 −12 扫到 +12 共 24 个半音，输出音高**纹丝不动** |
| 听着像一坨糊 | 旋律轮廓相关接近 0，音高起伏比接近 0 |

而且排查成本极高：分离、变声、混音三步全对，成品照样没法听——因为模型本身是废的。
（为定位这一条，实测过：换模型、换 fp16/fp32、关 CUDA graph、直接监视送进模型的
`pitchf`——最后确认 `pitchf` 是对的、声码器也是对的，是模型自己不跟 f0。）

现在的行为：

1. **训练前自动备好底模**：本机没有就去下载（v1/40k 是 `assets/pretrained/f0G40k.pth`
   与 `f0D40k.pth`，共约 175MB）。下载源优先国内镜像，失败才回退 HuggingFace。
2. **下载不到就硬失败**，不会"没底模也接着训"——因为那样交出去的是个废模型，
   用户只会以为是自己的素材不行，永远找不到真正的原因。
3. **RVC 只在没有旧断点时才加载底模**（`train.py` 里 `-pg` 是在
   `except: 无法加载已有断点` 这个分支里才执行的）。所以：
   **在旧模型上续训，底模依然不会生效。** 界面上因此给了
   「从头重训（换用底模）」勾选项；角色的歌声模型若是无底模训的，会直接标红提醒，
   并且不勾这个选项就会被拦下（免得白等几十分钟）。
   旧断点会挪到 `logs/<角色>/_从零训的旧断点/` 保留（移动不是复制，不额外占盘），
   预处理好的特征会复用。
4. **唱歌时会提醒**：角色绑定的模型若记为「无底模」，任务日志里会明说
   "这是从零训的，唱不对不是素材的问题，用底模重训一次就好"。

## 成品客观质检：把「难听」变成能对账的数

只在分离上做对还不够——变声那一步也可能静默失效（设了 pitch 却没生效、旋律被唱平、
人声和伴奏错位）。听起来都只是"难听"，谁都说不清难听在哪。

所以每次唱歌都会用 RVC 自带的 RMVPE（**和推理链里同一个 f0 提取器，口径一致**）
把「原唱人声轨」和「角色人声轨」逐帧比基频，量出：

| 指标 | 含义 | 正常 |
|---|---|---|
| `shift_semitones` | 实测整体平移了几个半音 | 应当≈你设的 pitch |
| `match_ratio_loose` | 去掉平移后，±150 音分内的比例（**主判据**） | ≥ 70% |
| `match_ratio` | 同上但口径收紧到 ±50 音分（**只作参考**，见下） | ≥ 50% |
| `octave_err_ratio` | 偏差落在 900~1500 音分的比例（**八度错**） | ≤ 15% |
| `spread_ratio` | 角色音高起伏 ÷ 原唱音高起伏 | ≥ 0.5（≈0 = 唱成了平线） |
| `contour_corr` | 旋律轮廓相关（固定 @0ms） | ≥ 0.5 |
| `lag_ms` | 人声与伴奏的时间错位（用「唱/不唱」图案量的，见下） | ≤ 250ms |
| `clip_ratio` | 削幅采样占比（会破音） | ≈ 0 |

**三条踩过的坑，现在都写死在尺子里了：**

- **音准统计固定 `lag=0`，绝不搜时间偏移。** RVC 内部会垫 3 秒再裁掉，而混音是按
  **样本**对齐的，两条轨本来就该差 0。一开始按「f0 轮廓相关最大」去搜偏移，它挑到
  **−130ms**（该处轮廓相关 +0.960，竟比 0ms 的 +0.950 还高），再在这错位处算吻合率
  ⇒ 同一份成品从真实的 83% 掉成 **43.7%**，直接报"失败：音准吻合只有 44%"，
  把一次**合格的**变声判成了不合格。根因是旋律轮廓天生平滑，两条平滑曲线错开一点点
  相关系数不掉反升，所以"相关最大"这个标准**天然偏向"错开一点点"**的位置。
- **±50 音分在人声上没有判别力。** 颤音/滑音让 10ms 一帧的基频一直在动。尺子自检：
  拿 `librosa.effects.pitch_shift` 精确降 12 个半音（真值偏差恒定 0），这个口径只读到
  **47.2%**、逐帧偏差四分位距 1167 音分——一个"完美"的变调都过不了它。所以主判据
  换成 ±150 的宽松口径，±50 降级成参考值。
- **光看吻合率抓不住"唱成一条平线"。** 它是去掉整体平移之后算的——一条完全不动的
  直线每帧偏差都是 0 音分，吻合率反而是 **100%**。所以必须再量 `spread_ratio`。

**错位检测改用「唱 / 不唱」图案，不改用 f0 轮廓。** 图案（某帧到底有没有基频）不随时移
平滑，比 f0 轮廓可靠得多——这也是它不能被用来纠音准的原因（一旦拿它把时间轴挪来挪去，
就又回到上面那个坑里了）。所以分工是固定的：**音准永远在 `lag=0` 处量，错位这条数
只负责自己报告错开多少**（>250ms 判失败，提示"对齐有问题"），两条结论互不污染。
门禁里专门有一条守这个：「错位不会污染音准结论（lag 报错位、match 报音准）」。

**门槛是量出来的，不是拍的。** `verify_qc_ruler.py` 用单调扫频 + 乐句停顿合成素材，
把正确版本和四种坏版本并排跑：same ≥ 0.98 / reversed ≤ 0.45（轮廓 ≤0.30）/
shuffled ≤ 0.70 / delayed 必须报 +300±40ms。用"几个音来回跳"的旋律做过一次，
倒放后还有 53.8% 命中率——**素材本身让尺子红不了**，换成单调扫频才有分辨力。

同样被换掉的还有"清辅音帧谱相似度"：拿它去量四个不同的 `protect` 值，结果全落在
0.987~0.991，**完全没分辨力**。咬字改用量 ASR 字错误率（见下面 RVC 参数一节）。

质检只取 **30 秒窗口**，不整首比：一首歌的旋律本来就大量重复，在两百秒里搜"最像的
位置"很容易锁到另一段副歌上（实测整首比会报"对齐差 1200ms"，而同一段 12 秒窗口里是 0ms）。

尺子本身在两个地方用**已知答案**自证过：`verify_qc_ruler.py`（上面四组正/负对照）、
`verify_sing.py`（抬高 7 个半音 → 报 +7.01；垫 500ms → 报 +500.0；换一条完全不同的
旋律 → 轮廓相关掉下来；成对判据"成品里有没有原唱"还配了旧做法当负对照）。

## 多轨试听台：让你自己定位是哪一步坏了

只给一条混好的成品，用户只能说"难听"。所以每条唱歌成品都带四条轨和一组工具：

- **分轨切换**：成品 / 人声（干声） / 伴奏 / 原曲
- **A/B 交叉淡化对比**：原曲与成品**同步播放**，滑块决定听哪边，两条始终对齐
  （不对齐的话比的是两个时间点，反而误导人）
- **变速慢放** 0.5× / 0.75× / 1×（浏览器内置慢放不变调），揪跑调和错位很有效
- **客观质检徽章**：音准 / 起伏比 / 对齐三项直接标在卡片上，不达标会标红并说明原因

老产物没有分轨信息（字段是后加的），会自动退回一个普通播放器，不会听不了。

## 改词唱：把原词换成新词，旋律照唱

**RVC 是音色转换器，它改不了词。** 想让角色唱新词，必须先用新词造一条"干声"，
再拿 RVC 把音色换掉。所以改词那一步插在**分离之后、变声之前**：

```
① 分离 → ② 改词（YingMusic-Singer-Plus，用新词重唱）→ ③ 估音高 → ④ RVC 变声
                                    → ⑤ 非歌声段保护 → ⑥ 混伴奏
```

- **引擎**：`D:/AHC/YingMusic-Singer-Plus-main` 的 YingMusic-Singer-Plus（第三方 SVS，
  本机第三套 python，与 RVC / GPT-SoVITS 那两套**互不 import**，全走子进程）。
- **按 28 秒分块改**，每块**强制 crop/pad 回输入长度** —— 不这么做 SVS 输出的长度会和
  输入差一点，攒到后面伴奏就错位了（漂移 > 0.4 秒会当场打 ⚠）。
- **歌词走文件传**（`--orig-file` / `--new-file`）：命令行直传带中文引号的字符串会炸。
- **代价**：改词比普通翻唱慢得多 —— 4 分钟的歌要多十几分钟（≈ 50 秒加载 +
  每块 90 秒）。所以界面上直接写了"建议先试听小样确认"。
- **句数/长度必须和音频时长配得上**：4 个短句配 30 秒音频 ⇒ 后段会乱唱（ASR 实测过）。
  改词区的句数提示就是为这件事服务的。
- **怎么验它真的改了词**：**ASR 对照**。改词前识别出"歌声是翅膀…"，改词后新词骨架全中。
- 只填一段或两段都不填 = 普通翻唱（改词是可选的）。

### 原歌词自动认出来，不用自己抄

改词台里的「原歌词」栏以前**得用户自己一句句抄一遍** —— 而"抄歌词"恰恰是最该交给机器的那一步。

现在改词区有个 **「自动识别」** 按钮：按下后从歌里把歌词认出来、填进原词栏，用户只写新词就行。

链路：复用已有的**分离缓存**（不重复分离）→ `faster-whisper`（`beam_size=5` + VAD 过滤，
拿**词级时间戳**）→ 按标点折成「句」→ `opencc` 繁转简 → 回填输入框。

- **为什么不用整合包自带的 ASR**：它输出的是"整首歌拼成一行的文本"，**没有时间戳**；
  而改词必须按时值分句 —— 句数和音频时长配不上，YingMusic 会把后段唱乱。
  它识别中文走 FunASR，在**歌唱**上的识别率也不如 Whisper。
- **Whisper 的中文输出默认是繁体**（实测"腐蝕的靈魂 黃金的戰神"）。给用户填进框里的
  必须是简体，否则他还得先自己转一遍 —— 那就等于没做。
- **分句规则**：遇句末标点立即断；遇逗号类标点且已攒够几个字也断；单句超过 14 秒或
  22 字**强制**断（否则一句被唱成 30 秒，新词会被摊到整段旋律上，节奏必然乱）。

**踩过的坑：整段间奏会被算进上一句。** 原来的实现只在"攒够长度/遇到标点"时收尾，
于是原唱唱完一段就进 20 秒间奏时，下一句的起点被并进了同一句 —— 实测最长句
**25.10 秒**、超过 14 秒的句有 3 句。修法是加一条**空洞断句**：上一句已经唱完
（上一个词结束），到下一个词开始之间**隔了 > 1.0 秒**就先把手里的收尾（`end` 用上一个词的
结束时间，不是下一个词的起点）。修完同一首歌最长句 **25.10 秒 → 8.30 秒**，
超 14 秒的句 **3 → 0**。

真浏览器验收 `verify_lyric_ui.py`（22 项，全部真鼠标）：折叠区默认收起、点得开、
框有面积、句数一致/不一致时提示分别正确（带负对照）、清空回到默认文案、
口哨段下拉三档齐全且默认 `keep`、**未选歌时点自动识别不进识别态**（负对照）、
点了之后进入识别态、结果真回填且已转简体。实测回填 546 字 / 25 句。

诊断用：`stages/lyrics_asr.py --dump-words` 会把词级时间戳整份写到 `<out>.words.json`，
分句一不对劲就看它。

## 提升效率 / 质量的三件事

### 1. 先听 30 秒样片（省下十几分钟干等）

整首歌的 RVC 变声是这条链里**唯一**的长耗时步骤（本机 3 分 45 秒的歌 → 约 18 分钟）。
用户改一个音高就要重等一次，效率极低。

「先听 30 秒样片」按钮：分离照做（有缓存），但只拿其中 30 秒跑 RVC
（从 35% 处起，避开前奏，通常是主歌/副歌）。整条链一两分钟就能听。
小样**不占用**成品清单的名额 —— 它固定叫 `*_preview_latest.wav`，每次覆盖上一条。

### 2. 音高自动估计（不是查表，是量出来的）

`stages/pitch_cli.py` 用 RVC 自带的 RMVPE（和推理链同一个 f0 提取器）分别量
**原唱人声**和**角色参考干声**的基频中位数，再算 `12 × log2(角色 / 原唱)`。

它对上了社区经验值，但是数据驱动而不是写死：
女声原曲给男声唱 ≈ −12，男声原曲给女声唱 ≈ +12，同性别 ≈ 0。

实测（原唱 263.0 Hz / 角色 98.9 Hz）⇒ **−17 半音**。

已知偏差：角色参考素材多半是**说话**声，而说话的基频中位数低于同一个人唱歌时的音域，
所以自动值会**偏大一点**。界面上会写明这一点，并建议往正数再调 2~4。
拿不到结果时返回 0（不变调）并说明原因 —— 宁可保守，也不瞎猜一个数让整首歌报废。

### 3. RVC 音质参数显式化

以前一个参数都没传，等于把音质交给 RVC 的默认值。现在显式写死：

| 参数 | 之前 | 现在 | 为什么 |
|---|---|---|---|
| `--f0-method` | rmvpe（RVC 默认） | **fcpe** | 逐帧基频提取器。实测在"口哨 + 人声"混在一起的素材上更稳 |
| `--rms-mix-rate` | 1.0（RVC 默认） | **0.25** | 1.0 = 输出响度包络 100% 抄输入音频，句尾会突然掉下去；0.25 是 RVC 官方 WebUI 的默认值 |
| `--protect` | 0.33（默认） | **0.33**（显式） | 保护清辅音/呼吸不被音色污染。**必须 < 0.5**：RVC 源码里是 `if protect < 0.5` 才启用这段保护，所以 **0.50 等于把保护完全关掉**。显式写是为了将来 RVC 改默认值时不跟着飘 |
| `--index-rate` | 1.0（RVC 默认） | **0.50** | 检索强度。1.0 会过度"检索"而吞字，太低音色不稳 |

**`protect` 的方向是实测出来的，不是照抄默认值。** 中途一度把它从 0.33 "调高"到 0.50
（以为数值越大保护越强，实际是关掉了保护），代价直接落在咬字上。用 **ASR 字错误率**
当"咬字清晰度"的客观代理量了四个值：

| `protect` | ASR 字错误率 |
|---|---|
| 0.50（= 保护关闭） | **70.5%** |
| 0.40 | 54.1% |
| **0.33（现在）** | **54.1%** |
| 0.20 | 52.5% |

0.20 略好一点点但音色稳定性更差，所以取 0.33。为什么要绕道 ASR：直接量"清辅音帧的
谱相似度"量不出差异（四个值全在 0.987~0.991），**没有分辨力**，换个角度才能看见差别。

## 暂停 / 继续

任务卡右侧的 **⏸** 按钮，点一下挂起，再点 ▶ 从原地接着跑。

- **真的挂起进程**，不是"界面上不动了"：用 `ntdll.NtSuspendProcess` 挂起整棵进程树。
  挂起后显卡/CPU 立刻空出来。
- **必须连后代一起挂**：`run()` 用 `shell=True`，Windows 会先拉一个 `cmd.exe`，
  真正干活的是它下面的 `python.exe` —— 只挂根进程等于没挂（实测：按了暂停计数照涨）。
- **已用时间与 ETA 会扣掉暂停时长**：否则暂停十分钟再回来会显示"已用 28 分钟"。
- 任务落盘时带 `paused` 状态，但**不落 `_paused_at`** —— 服务重启后子进程早没了，
  把"正在暂停中"带回来只会让它永远停在那。
- 实测：暂停后 3.5 秒计数增长 **0**，恢复后 2 秒增长 20（正常速率）。

## 取消任务（不只是暂停）

任务卡右侧的 **✕** 是取消（⏸ 是暂停，两回事）：

- **真杀进程树**，不是"标记一下等它自己发现"：用 `taskkill /T /F` 连子孙一起杀。
  只杀根进程没用——`run()` 用 `shell=True`，真正干活的是 `cmd.exe` 下面的 `python.exe`。
- **暂停中也能取消**：先 `NtResumeProcess` 恢复挂起的进程，再杀。直接杀挂起进程
  在 Windows 上会留下僵尸。
- 状态落成 `cancelled`（不是 `failed`），步骤清单里那条"正在做"标成 `cancel`，
  界面上不会永远挂着一个"正在做"。
- **已结束的任务不能取消**（点 ✕ 会直接被拒，不弹确认框）。
- 确认框里可以勾选「顺手删掉中间产物」，省得再自己去存储面板里找。
- `_kill_pids` 显式排除本进程 PID——否则服务会把自己的子进程树（含挂着的浏览器）一起杀掉。

## 存储清理（删训练权重，腾地方）

顶栏 **存储** 按钮打开。按组分好（RVC 权重存档 / RVC 断点 / 说话模型 ckpt /
任务中间产物 / 上传原片 / 分离缓存 / 回收站），每项带大小、路径、mtime。

保护规则（默认勾不上）：

| 锁 | 谁 |
|---|---|
| 角色正在用的模型 | 唱歌权重 + 同名索引库、说话模型 ckpt |
| RVC 底模 | 所有歌声模型的起点，删了要重下（huggingface 在本机 000，只能走镜像） |
| 运行中任务 | `data/jobs/<id>` |

想删被锁的（比如这个角色已经不想要了，想把它的权重一起清掉）：打开 **🔓 允许删除角色在用的模型**，
那一行会变红、可以勾。删掉之后**会同步清掉 `roles.json` 里的引用**——否则界面上
角色还在、按钮还能点，一跑才报"找不到模型"，用户根本想不到是自己刚勾掉的那项造成的。
底模和运行中任务**打开 🔓 也删不掉**（那是真的不能删）。

**悬空引用警告（这一条是真踩出来的）**：角色记着"我有模型"但那个文件已经不在了
（手工删过 / 早期版本清理误删），界面上必须当场喊"要重训"，而不是让人以为唱歌坏了。
这里踩过一个真 bug：面板的扫描结果有 2 分钟缓存，而前端"打开面板"时**有缓存就直接
渲染旧的**——用户删了模型再打开面板，警告永远不出现。修法是两层：
`warnings`（只读 roles.json + 几个 exists，微秒级）**每次实时算、不跟着缓存走**；
前端每次打开面板都重新拉一次（昂贵的磁盘扫描仍走缓存）。

两个实测出来的坑：

- **删完磁盘剩余数字不会立刻变**。本机 D 盘写入立刻掉空间、删除却有滞后
  （实测写 0.3G 立刻 −0.3，删掉后数字纹丝不动）。所以界面上写着"系统统计可能有延迟"，
  别因为数字没动就以为没删掉——看列表里那一项是不是消失了。
- 每次删除都写一份清单到 `data/_trash_log/deleted_<时间>.txt`（纯文本几 KB），
  真出问题至少知道删过什么。

## RVC 训练链路（这一版的坑，都已绕过）

本机 RVC 版本较新，训练脚本的调用方式与老教程不同，`train_rvc()` 里按实际脚本处理：

| 环节 | 实际调用 | 说明 |
|---|---|---|
| 切分 | `train/preprocess.py <数据集> 40000 4 <logs/exp> True 3.7` | 采样率是**数字** |
| 基频 | `train/dataset/extract_f0.py cuda 1 0 0 <logs/exp> True` | 脚本在 `dataset/` 子目录 |
| 特征 | `train/dataset/extract_hubert_feature.py cuda 1 0 0 <logs/exp> v1 True` | 用 cnhubert，不需要 fairseq |
| 训练 | `-m train.train -e <exp> -sr 40k -f0 1 -bs 4 -te N -se 15 -g 0 -sw 1 -l 1 -c 0 -v v1` | 必须 `-m`；`-sr` 是 `40k` 不是 `40000`；`-sw 1` 才存权重 |
| 索引 | `train/train_index.py <exp> v1 <assets/indices> <cpu数>` | 没索引唱歌会自动降级 index-rate 0 |

两个必须自己做的前置（WebUI 平时替你做了）：
1. `logs/<exp>/config.json` —— 从 `configs/v1/40k.json` 拷一份
2. `logs/<exp>/filelist.txt` —— 每行 `wav|特征npy|f0.npy|f0nsf.npy|0`，缺特征的行要跳过

**必须用 `-m` 的原因**：直接 `python train/xxx.py` 时 `sys.path[0]` 是 `train/` 目录，
里面的 `train.py` 会被当成 `train` 包抢先导入，导致 `from train import utils` 循环导入。

### 训练第 1 轮就崩 `PermissionError`（RVC 自己的偶发竞态）

`train/data_utils.py` 在 DataLoader worker 里「首次用到才写」`*.spec.pt` 缓存，
既没加锁也不是原子写；`num_workers=4` 在 `train/train.py` 里写死（配置和命令行都改不了），
于是 Windows 上偶发：

```
PermissionError: [Errno 13] Permission denied: ...\logs\<exp>\0_gt_wavs\14_2.spec.pt
```

表现是**训练在第 1 轮就挂掉**，甩一句看不懂的英文 —— 很容易被当成"素材坏了"。
`train_rvc()` 里认出这个特征（`PermissionError`/`Errno 13` **且** 提到 `.spec.pt`）后
**自动重跑一次**（最多两次）：崩过之后大部分缓存已落盘，重跑时竞争窗口小得多。

★ 认错的范围卡得很死 —— 显存不够、别的 PermissionError、正常结束**都不触发重试**。
认宽了就会把真正的训练错误也重跑一遍，让你干等十几分钟再看一次同样的报错
（`verify_rvc_train` 里有三条负对照专门钉这件事）。

### 删角色会漏掉 RVC 那边的 1 GB

一个角色在 RVC 目录里躺着 `logs/<id>/`（G/D 两个断点约 1 GB）、权重 52 MB、索引几 MB。
以前 `delete_role()` 只删**本项目**的角色目录 ⇒ 每删一个角色就往 RVC 目录里扔 1 GB
拿不回来的垃圾，界面上还看不见、也没有入口再删。现在 `delete_role()` 会顺着
`rvc_artifacts()` 把这三处一起清掉（逐项容错 —— 本机删除钩子抛 `SystemExit`，
`except Exception` 捕不到，不逐项接会把整个进程掀翻）。

在那之前已经漏掉的，跑一次清：`bash _run_regression.sh gc`（第二段专门扫 RVC 孤儿，
且**先删大的**：删除预算只有 50 次，而 G/D 那两个文件就占了目录体积的 96%）。

## 角色卡上「能干什么」（这一版加的）

### 为什么卡片以前在骗人

装了 17 个市场角色之后，卡片一律写着「未训练」—— 这三个字说的是「没有**说话**
模型」。而这些角色的**歌声模型是现成能用的**，用户看到「未训练」只会以为整张卡
是废的；反过来，卡片上那个「💬 TA 说话」对它们又是**点了必然失败**的：`speak_role`
第一句就校验 `role["model"]`，用户得填好文字、点合成、看着任务跑起来、等几秒才收到
一句红字。而原来那句预警写的是 `if (r.kind === "speech" && !r.model)` —— 市场角色的
`kind` 全是 `"singing"`，所以**一句预警都不会出现**。

### 改法：能力算在服务端，界面只负责显示

`studio.role_ability(r)` 每次读的时候现算（**不持久化** —— 素材一加、模型一训就该
变，写进 `roles.json` 就等着出现过期的「可说话」），说话 / 唱歌各自三态：

| 状态 | 含义 | 卡片上 |
|---|---|---|
| `ready` | 现在就能出成品 | 绿 · 🎤 可唱歌 / 💬 可说话 |
| `trainable` | 素材够了，训一次就行 | 黄 · 可唱歌（先训一次） |
| `blocked` | 还差素材 | 灰 · 还不能唱歌 |

三条规矩：

1. **判据只写一份**：`role_ability` 看的字段必须跟真正执行任务的 `speak_role`
   （`role["model"]`）/ `sing_job`（`role["rvc"]["model"]`，且素材 ≥10 段、每段 ≥2 秒）
   **完全一致**。放宽一点，用户就会看到一个绿色的「能用」然后点下去失败 ——
   那比不显示更糟。`verify_ability` 的 B 段就是钉这件事的。
2. **走不通的入口不删、只弱化**：按钮还在、还点得动，点进去能看到为什么（页面顶部
   一条状态条说清「为什么不能」+「下一步该干嘛」）；说话页的合成按钮则直接灰掉 ——
   那一步点下去只会白等一次。
3. 卡片上不再有「未训练」这种**只说一半**的说法；打开角色第一眼（简介页）就能看到
   唱歌 / 说话两行总览。

### 顺带踩的坑：CSS 类名撞车把别人的布局撑塌了

新加的状态条我一开始用了 `.ab` 这个短名字，而**翻唱台的分离轨道那边已经在用
`.ab`**（`style.css` 里的 `.stems .ab`）。于是新规则跑过去给那些元素加上了
`padding` / `border` / `background`，翻唱台控制区被撑塌 —— 表现是「自动识别原歌词」
和「一键合成」两个按钮**算出来同一个坐标**，真鼠标点哪个都点不到，`verify_lyric_ui`
一下红 4 条。

这类问题在截图上几乎看不出来（元素都在，只是叠在一起），**只能量几何**。所以：

- 新样式一律带前缀（现在是 `abk-`），加之前先 `grep` 一遍类名；
- 抓住它的是 `verify_lyric_ui` —— 靠的是「点了按钮有没有进识别态」这条**行为**判据，
  所以别把那条当成重复的删掉。

## 判据（自动验收口径）

- 合成体检：无 NaN、RMS 正常、削幅为 0、语速 < 1 秒/字、静音 < 50%。
- 声音分离：eres2net 声纹 + 时间相邻聚合聚类，112 段正负对照 ARI 0.93，
  端到端（AAC 压缩 + UVR 后）双人交错视频准确率 0.96。
- 相似度只打印作参考，不判成败——实测它区分不出「像不像本人」。
- 删角色：`delete_role` 里 `rmtree(..., ignore_errors=True)` 的失败会被**复核**一次并告警
  （stderr 进服务日志）。因为它是"先摘角色库登记、再删目录"，删目录那步一旦失败
  （文件被占用 / 权限 / 被安全策略拦），角色就从界面上消失、文件却永远留在盘上 ——
  用户既看不见、也再没有入口去删它。`studio.orphan_role_dirs()` 专门把这类
  **幽灵目录**列出来（含占用大小），门禁 `verify_speaker_match` 收尾就用它复核。

★ 跑门禁时**一次只跑一关**：`bash _run_regression.sh verify_storage`（不传参数 = 全部串行）。

原因不是"脚本写得慢"，而是**本机环境层有个批量删除钩子**：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn", ...}
```

它按**当前这条命令里累计删了几次**计数（`scope:"turn"` 的"turn"实测就是**一次 Bash 调用**，
不是整个会话），阈值 50。把六关塞进一条 `for` 命令里跑，前面几关就把额度吃光了，
之后**每一个删除都被挡下**，脚本就在清尾处被掐断。
（实测对账：同一会话里，那六关中的 `verify_seedvc` / `verify_sing` / `verify_ingest_batch`
在被掐断时**一条 `! FAIL` 都没有**、只是没打出汇总行；改成"一关一条命令"重跑，
分别拿到 37/0、41/0、17/0 全绿，退出码 0 —— 所以看到"没汇总行就 EXIT=1"的门禁，
先去数它这一条命令里前面还跑了几关，别急着判产品坏了。）这不是项目代码、也不是沙箱——
把沙箱整个关掉照样拦。注意 `count` 报的是**累计数**而不是"这次删几个"：被拦的那一条
`count=50` 而 `targets` 里只有**一个** 1MB 的探针文件，所以别按"文件多不多"去理解它。

**它拦人时抛的是 `SystemExit`，不是普通异常**（查清了，这条很关键）：
`except Exception` **捕不到** `SystemExit`。症状就是"整个门禁跑到收尾处静默死掉、
连汇总行都不打"，看着像"这一关挂了"，其实前面全绿。所以门禁里凡是删东西的地方都写成
`except BaseException`；`verify_speaker_match` 因此改成"摘登记用 `delete_role`、
**删目录只对自己刚建的角色逐个 `os.remove`**，最后再用 `studio.orphan_role_dirs()`
复核真没留孤儿目录"。

补一个**已经量过的小事实**，免得后人又去瞎猜钩子在数什么：同一台机器上，
一次命令里**逐文件 `os.remove` 60 个真 40KB 文件、或连做 60 次只装 1 个文件的
`rmtree`**，都不会被拦；被拦的是"门禁这种要跑一堆子进程、最后批量删真角色目录"的
场景。所以**别按"删了几个文件"去调预算，按"这个脚本要不要建/删真角色"去判断**。

被掐断的样子有三种，第三种最坑：

1. **整个脚本一行输出都没有**（连横幅都不打）—— 因为 `import studio` 时 studio 的启动
   清道夫就在删老垃圾，一进门就被拦；
2. **判据全部 PASS 但没有汇总行**，退出码非 0 —— 看着像"这关挂了"，其实判据全过；
3. **判据真的报 FAIL**，因为它量的就是"东西被删掉了没"，而删除被钩子挡了。
   `verify_jobctl` 的「中间产物被清掉」就是这么假红的 —— 这条**最容易被当成产品 bug**。

实测：13 关挤在一条命令里跑，`verify_sing` / `verify_storage` / `verify_jobctl` /
`verify_train_rounds_ui` / `verify_lyric_ui` 五关栽在这上面（其中 jobctl 报的是第 3 种假 FAIL），
**同一份代码逐关重跑立刻全绿**（24 / 34 / 51 / 62 / 46 / 22 项，0 失败）。
`verify_speaker_match` 是**第 4 种**：它自己建真角色、收尾要删，于是被拦在**收尾**处 ——
前 24 项全绿却连汇总行都打不出来（`SystemExit` 穿透 `except Exception`）。
所以：判红先看有没有 `safe-delete` 字样，有就作废重跑，别去改产品。

**子进程的输出必须在它结束之前就出现在日志里**。根因是 Python 在 stdout 接管道时
默认**块缓冲（4~8KB）**——`subprocess.Popen(..., stdout=PIPE)` 又不设
`PYTHONUNBUFFERED`，子进程的 `print` 就全堵在自己缓冲区里，直到进程退出才一次性冒出来。
表现出来就是"点了一键唱，十几分钟一个字都没有，像死机"。判据自带负对照：
同一条命令，把 `PYTHONUNBUFFERED` 摘掉后**必须抓不到早到的行**，否则这条判据是假的。

新写的判据要先证明它**能红**，不能只因为它绿了一整轮就信它。
`verify_ingest_batch.py` 的 5 条核心判据都用 `_probe_ruler_batch.py` 做过尺子自检：
把被测行为换成坏版本（覆盖人工文本 / 新素材不挂 / 不去重 / 合并时按源分组 / 漏传
`append_to`），再拿门禁里同一条判据表达式算一遍，**每条都必须变红**——不红就说明
那条判据量的根本不是我以为的东西。实测结果：5 条会红、0 条坏了还绿。

## 声音市场：搜别人训练好的模型，挑中哪个下哪个

**不想自己训？直接搜别人训好的音色，下完自动变成一个能唱的角色。**

```
网页「🎭 声音市场」→ 点作品（小马宝莉 / 地狱客栈 / 原神…）或自己搜 → 点「安装」
   → 下载 → 解压 → 权重放进 RVC → 索引对上 → 真的 torch.load 一次 → 建角色卡
```

省掉的手工活正好是最容易错的那几步：改文件名、放对目录、让索引对上、确认能加载。
少做一步的症状都是"模型加载失败"或者"唱得出来但检索没生效"，而用户根本无从判断
是**模型本身有问题**还是**少放了一个文件**。

### 装完就是中文名（字典 + 音译，纯本地，不联网不花钱）

装进角色库的名字一律先翻成中文，**原名永远留在简介和别名里**（`原名 XXX · 来自声音市场（repo）`），
翻错了你一眼能对着原名核对。2026-10-13 之前装的那批也是这么补的：不用重装，
每次装完会自动把库里还挂着英文名的市场角色一起补译。

谁能被改、谁不能被改，界线写死在代码里：

| 情况 | 动不动 |
|---|---|
| 来自声音市场、名字还是英文 | ✅ 译成中文 |
| 来自声音市场、现名**本来就是我们译出来的**（等于译名、或译名 + 我们加的后缀） | ✅ 允许按新字典重新取名（撞名后缀也会跟着更新） |
| 来自声音市场、但你**亲手改过**名字 | ❌ 一律不动，那是你说的算的 |
| 你自己建的角色 | ❌ 默认不动；想全量翻可以手动 `POST /api/roles/retranslate {"all":true}` |

★ 判不出来的情况（现名既不等于译名、又无法确定是不是你手打的）**一律不动** ——
宁可留一个旧译名，也不能偷偷把你的东西改掉。

三层，从上往下试：

| 层 | 怎么来的 | 例 |
|---|---|---|
| ① 确定译名 | 本地字典（276 条，翻译取自中文维基/引进版；拿不准的一条都不写） | `TwilightSparkle` → 紫悦、`FlurryHeart` → 风雪之心、`AdagioDazzle` → 阿达吉奥·达佐 |
| ② 写法纠错 | 连写驼峰、尾部 `V2`/`2`、拼错一个字母（本地 difflib，够像才认：0.90 且长度差 ≤2） | `TwilightSparkle` / `AdagioDazzleV2` / `AddagioDazzle` 都指向同一条 |
| ③ 音译兜底 | 按读音拼（声母×韵母表 + 词尾辅音，照《英语姓名译名手册》的取字习惯） | `BabsSeed` → 巴斯·塞德、`Daybreaker` → 代布雷凯尔、`Octavia` → 奥克塔维亚 |

**音译的安全边界**：它只用这个词的拼写，**不判断"它是谁"** ⇒ 永远不可能把
`Frieren` 说成「艾伦」（那是早年用子串匹配翻出来的真事故）。看着不像人名的
（带数字、`model/voice/test` 这类通用词、没有元音的乱串）一律不动，保留英文。

#### 同一个角色装了好几份时，名字怎么分

一个合集仓库里常常同时有 `AriaBlaze` / `AriaBlazeV2` / `AriaBlazeV3`，拼错的
`AddagioDazzle` 也混在里面 —— 全都翻成「阿里亚·布雷兹」的话，几张卡片长得一模一样，
你没法挑。两条规则：

1. **干净名给最正的那个写法**。按"谁更接近字典里的正写"排座次（字典精确命中 >
   剥掉版本尾才命中 > 拼错纠错 > 只能音译），**不是按安装顺序先到先得** ——
   先到先得会把干净名发给 `V2` 那个包，正主反倒挂着后缀。
2. **后缀一律取自市场原始压缩包文件名，绝不现编**。`Applejack_Talking_Singing_e320_s8000`
   减去角色名 ⇒ 「苹果嘉儿 (Talking Singing e320)」；`AdagioDazzleV3` ⇒ 「(V3)」；
   拼错的那个就用原名本身 ⇒ 「(AddagioDazzle)」。全都取不到才退成「第 N 份」。

**你自己改过的名字永远不会被改回去**：只有"现在这个名字本来就是我们译出来的"
（等于译名、或译名 + 我们加的后缀）才允许重新取名，判断不了的一律不动。

### 边界（写在代码第一行，也写在界面上）

只索引 Hugging Face 上**公开可下载**的模型，跟你在网页上手动点 Download 是一回事；
**不破解任何付费内容、不碰账号体系、不抓非公开资源，搜不到就是搜不到**。
下载来的模型仍遵循它自己的许可，每张卡片上都标了 license —— 商用前自己看。

### 作品预设与「全角色」的真实情况

HF 的搜索只按**仓库名/标签**匹配，而"小马宝莉"四个字在英文仓库里根本不出现
（他们叫 Twilight Sparkle、Rainbow Dash…）。所以预设里给每部作品写的是**搜索关键词**
（作品名 + 每个角色名各搜一遍），并且把**没搜到的角色照实列出来** —— 绝不编造。

实测（2026-10-13，会随 HF 上的模型增减而变）：

| 作品 | 搜到 | 没搜到的角色 |
|---|---|---|
| 小马宝莉 | 22 个仓库 | Discord |
| 地狱客栈 | 21 个仓库（Loren85 一批） | Lilith、Velvette、Rosie |
| 咒术回战 | 20 个仓库 | Panda |
| 鬼灭之刃 | 14 个仓库 | Tanjiro |
| 赛马娘 | 8 个仓库 | Silence Suzuka、Mejiro McQueen |
| 极恶老大 | 7 个仓库 | 无（全齐） |

（数字是当次实测，HF 上的东西天天在变；没搜到的角色界面上会照实列出来。）

★ **覆盖是靠"两轮搜索"撑起来的**，这一条最值钱：第一轮搜「作品名 + 角色名」，
第二轮**只对没搜到的角色单独搜角色名**。原因很实在 —— HF 的搜索是按**仓库名**匹配的，
而分享者只写 `teio-rvc`，压根不写作品名：连着搜 "Uma Musume Tokai Teio" **一个都没有**，
单独搜 "Tokai Teio" 能出 2 个真模型。实测赛马娘 0 → 8 个仓库、小马宝莉 3 → 22、
鬼灭 3 → 14、咒术 3 → 20。第二轮必须配**严格**过滤：单独搜角色名会捞回一堆同名 LLM
（搜 "Enterprise" 前三是 Llama / wav2vec / sd-vae）。

★ **「全角色」的关键在合集仓库**：这类作品在 HF 上大多是"一个仓库里塞十几个 zip"。
所以卡片上标「合集 · N 个角色 · 共 x GB」，并给你三种粒度：

- **装全部 N 个** —— 先弹确认把数量与体积说清楚（你自己决定下不下），每个包一步进度，
  某个包坏了跳过它继续下一个；
- **展开包列表，只装其中一个** —— 每个包一行、一个「装这个」按钮（包多时先摆 8 个，
  其余点「还有 N 个…」展开）。以前只有「装全部 / 只装第一个」，想要中间那个角色
  只能把整个合集下来，或者拿第一个自己根本不认识的角色；
- 单个角色的仓库就直接一个「安装」。

**按标签逛（想"找到更多"就从这个入口进）**：HF 上训音色的人大多会给仓库打
`rvc` / `singing-voice-conversion` / `so-vits-svc` 这类标签，按标签拉清单
**一次能拿 300 个仓库、还按下载量排好**（关键词搜索一次只有十来个，还混着同名 LLM）。
实测这个池子抽查 38 个，37 个真带权重。界面上是三个 chip（RVC 音色模型 / 歌声转换 SVC /
So-VITS-SVC），点一下出第一屏，底下「加载更多」一直翻。

翻页靠服务端**结果池**（`qid`）：一次搜索/浏览把候选清单存成池，文件清单只在
**真要显示的那一页**上问，问完记回池里 —— 首屏不用为第 10 页付费，翻回去也不用再问
镜像一次（镜像并发一大就随机 502，少问一次少一次抖动）。

**入库自动翻成中文角色名**：分享者清一色写英文（`Alastor-Hazbin-hotel-ita.zip`），
装进角色库就是一串认不出的英文。现在会按**本地字典**翻（Alastor→阿拉斯托、
Twilight Sparkle→紫悦、Tokai Teio→东海帝王），卡片上写中文，并把**原名留在简介里**
方便核对。两条硬规矩：① **纯本地字典，不调任何翻译接口** —— 不联网、不花钱、
不消耗积分，装一百个也是零成本；② 只翻确定的，拿不准的**留英文**，绝不硬编一个
看着像中文的名字（装错角色比名字难看严重得多）。

### 几个踩过的坑（都写进代码注释了）

- **搜索 API 不返回文件清单** ⇒ 必须逐个仓库再问一次才能知道"里面到底有没有权重"。
- **safetensors 不算音色模型**：HF 上绝大多数 safetensors 仓库是 LLM / 扩散模型
  （实测搜角色名 "Adam" 第一个结果是个情感分类模型）。只认 `.pth` / `.ckpt` / `.zip`。
- **但不能只认"名字里带 rvc/voice"**：Loren85 那批仓库只写「角色-作品-语言」
  （`Alastor-Hazbin-hotel-ita`）且只发一个 zip ⇒ 按旧规则自由搜索一个都出不来，
  连安装都被挡（还谎报"读不到这个仓库"）。真正的区分度在**文件后缀**上。
- **4xx 不能当网络错误重试**：镜像对不存在的仓库返回 401（0.75 秒），
  以前一律重试 3 次再换源，而第二个源要等 10 秒才失败 ⇒ 一个"查无此仓库"
  被拖到 60 秒以上。现在 1.4 秒答复，且**不缓存**网络抖动造成的空结果。
- **"没搜到" ≠ "没有"**：整批请求都被网络抖掉时会明确说"模型站这会儿连不上"，
  而不是让你以为世上没有这个角色。

接口：`GET /api/models/works` · `/api/models/search?q=` · `/api/models/work?key=` ·
`/api/models/detail?repo=` · `/api/models/installed`；`POST /api/jobs {"kind":"install_model"}`
（带 `all:true` 整批装）。

## 在线曲库（导歌）

翻唱台下方新增「在线曲库」：搜开放授权的歌，一键导进翻唱台②号槽。

**只接实测能整曲下载、且授权写在数据里的源。** 逐个机验的结果：

| 源 | 结论 | 原因 |
|---|---|---|
| **ccmixter** | ✅ 启用 | 搜索 / 许可 / 文件页 / 整曲下载全链路通 |
| **Free Music Archive** | ⚠️ 已实现，默认关 | 需渲染 JS，且曲目 URL 是**四层** `/music/<艺人>/<专辑>/<曲目>/`（藏在 `data-track-info` 属性里，不在 href）；实测 8 关键词 × 20 首=160 首里可商用 **0** 首，连续搜索还会被限流封禁。设`VS_FMA_ON=1` 开启 |
| jamendo | ❌ | v3 强制 `client_id`，无 key 返回 `code:5` |
| iTunes Search | ❌ | 只给 30 秒预览，且是商业版权曲 |
| pixabay / musopen | ❌ | 整站 403 |
| 耳聆网 | ❌ | Cloudflare 人机挑战 |
| openverse / archive.org | ❌ | 本机网络不通 |

**ccmixter 翻页**：`offset` 是唯一生效的翻页参数（`skip`/`page`/`start` 全被忽略）。
单页上限 **29** —— `limit>=30` 会返回 HTTP 200 + 空 body（**不是报错**，看起来像成功
其实什么都没有）。所以「多搜/深挖」是另走 `deep` 档位（29→87→145→203→261 首），
不是把 limit 调大。

宁少而真：不在界面摆搜不出东西的死源。注册表 `SOURCES` 是多源的，
以后哪个通了加一条即可，前端自动多一个标签。

**授权红线**：放行 CC0 / 公共领域 / CC-BY / CC-BY-SA；
**CC-BY-NC（禁商用）与 CC-BY-ND（禁改编）一律不导**——翻唱本身就是「改编」，
与 ND 硬冲突。NC / ND 不会消失，而是置灰并写明原因，由你自己决定。
默认只搜可商用（ccmixter 的 `lic=by`），因为该站默认结果几乎全是 NC。

下载是真下载：落盘前校验大小与文件头（不是音频就报错），
再用 ffmpeg 量真实时长，之后才填进翻唱台。同一首歌重复导会自动复用已有文件。

## 本地音乐导入（你自己下的歌）

在线源再多也是别人的开放授权曲，风格有限。你自己机器上的歌**直接就能用**——
导入自己的文件没有任何第三方问题。

**两条路，语义和代价不同，界面上写清楚了：**

| 做法 | 复制文件？ | 适合 |
|---|---|---|
| **填目录路径 → 扫描 → 全部导入** | ❌ 只登记路径 | 成百上千首歌；原文件留在原地，**能继续分轨编辑** |
| **拖单个文件 / 「添加单个文件…」** | ✅ 复制一份到 `data/music/` | 只想用一两首，不想先找它在哪 |

拖放这条路以前是**死路**：浏览器出于安全不会把真实磁盘路径交给网页，
点「添加单个文件」只会弹出一句"做不到"。现在改成上传文件**内容**，
由后端存进 `data/music/` 再登记 —— 浏览器给不了路径，但给得了内容。

### 校验（三道闸门，导入和上传共用同一条链）

1. **先嗅魔数再定类型**，不信扩展名。实测本机有 `.m4a` 其实是 AAC ADTS 裸流
   （真 m4a 第 5-8 字节是 `ftyp`，它是 `ff f1`）。
2. **最小体积闸门**。只验魔数会被假头文件骗过：`broken.wav`（17 字节文本）和
   `trunc.mp3`（只有 ID3 头）都能过魔数检查，到合成阶段才炸。
3. **真量时长**。写死 `dur=0` 会让界面看不出长短、RVC 前无法预判文件是否正常。

网易云/QQ/酷狗的**加密缓存**（`.ncm`/`.qmc`/`.mflac`）不处理，扫到会写明原因跳过。

### 候选目录（带真实歌数）

点一下就填进输入框，并且**显示扫到几首**——只给"存在/不存在"不够，
用户点一个 0 首的目录等于白跑一趟。注意「网易云音乐」指向
`%USERPROFILE%\Music\CloudMusic`（真能扫到歌），而
`%LOCALAPPDATA%\Netease\CloudMusic` 是**程序数据目录**，实测里面零歌曲文件。

#### 网易云 VIP 的歌在哪（这一版修的盲区）

探测**不写死路径**，因为客户端装在哪是用户自己选的。本机实测装在 `D:\CloudMusic`，
VIP 歌在它的 `VipSongsDownload` 子目录里——这个目录**不在** `%USERPROFILE%\Music` 下，
所以以前那个候选列表永远找不到 VIP 歌。这一版补了两处：

- **根目录也纳入探测**（`D:\CloudMusic` 自己），并对父子目录去重——根目录下还躺着
  2 首真歌，只探子目录会漏掉。
- **程序目录剪枝**：客户端自带 `resource/`（里面是「一起听」的 4 个提示音 wav）、
  `locales/`、`webapp*/` 等，不剪掉就会把这些提示音当成歌列给你。
  剪枝名单按前缀匹配（`webapp91x64` 这类带版本号的目录名也躲不掉）。

⚠️ **剪枝要在所有入口一起生效**：`dirs` 接口剪了、`scan` 接口没剪，
界面上就会出现「chip 写 5 首、点开 9 首」的打架——`verify_nav` 第 ⑤ 条专门钉这个。

⚠️ **监视目录要精确到子目录**：自动解密守护 `ncm_watch` 用 `os.listdir` 非递归扫描，
探测返回根目录后它就再也看不见子目录里的 `.ncm` 了（顶层 0 个，守护等于全瞎）。
所以另给了 `local_lib.ncm_dirs()`——**收集真正装着 `.ncm` 的那一层**，守护用它。

### 曲库不会静默丢歌

导入只登记路径，代价是原文件被移动/改名后链接会失效。所以：

- 文件不在原位**照样列出来**，标红写明「文件已不在这个位置」，而不是从列表里消失
  （以前 `local_library()` 直接 `if os.path.isfile(p)` 就丢弃 ⇒ 那首歌在界面上
  人间蒸发，用户既不知道丢了哪首，也没法找回）。
- 提供**重新定位**（指向新路径，同样过三道校验）和**从曲库移除**
  （只删记录，**绝不动你的文件**）。
- 状态是**每次读时算出来的**，不是"发生过就永久记账"——文件放回来，标记自动消失。

## 已知边界（如实说明）

- 体检能拦「崩溃级」问题（无声、乱语速），**拦不住「音色微妙不像」**——
  不满意就用更高档位重训。
- 唱歌/说话的自动判断是弱预判（置信度仅供参考），以手动选择为准。
- 第二次训练 = 用当前素材从头再训（不是断点续训），
  因为 lightning 的 last.ckpt 在 torch 2.6+ 下加载不了。
  **RVC 是例外**：`train/train.py` 自己会从 `logs/<exp>/G_*.pth` 续训，
  同一份素材连着训第二次会接着上次的轮数继续（目标轮数 > 已训轮数才会多训）。
- 「已训到 N 轮」是从 `logs/<实验名>/G_*.pth` 里读的。如果这个实验的权重目录
  被清理过、读不到文件，就显示 0 轮——此时按「从 0 开始」处理，不会拦你。
- 说话模型自定义轮数上限 200、唱歌上限 5000，超出会被自动收进上限。
  这两个数是「过头就崩」和「官方默认 20000」之间取的保守值，不是模型本身的限制。
- 从别处拿的 RVC 模型若没有特征索引库，会自动降级 index-rate 0（细节略少，不失败）。
- ASR 识别的人名/英文偶尔会出错，建议训练前点开角色页扫一眼文字。
- **自动识别的歌词同样会有错字**（歌唱的咬字比朗读难识别）。界面上直接写了
  「识别难免有错字，请核对后再写新词」。它省的是"抄一遍"的工，不是"校对"的工。
- 成品质检的**八度错**（偏差落在 900~1500 音分）会参与成败判定（>15% 直接判失败并说明），
  但**不会自动修** —— 修它要重跑整条 RVC 链路（十几分钟），没有可靠的自动判据之前不动手。
- 删掉角色**不会**连带删掉它的训练权重（那几 GB 是慢慢攒出来的，删错了没法 undo）。
  角色记录没了之后，那些权重在存储面板里就变成"没人用"的可清理项，自己去勾掉即可。
  （本机现在就有一份这样的 `r8c323d43.pth`，52.5 MB。）
- **声音市场的覆盖取决于 HF 上别人到底传了什么**，本项目只索引公开可下载的模型，
  不编造结果 —— 点「小马宝莉」时界面会把没搜到的角色名**照实列出来**。
  目前（2026-10-13）小马宝莉 16 个预设角色里有 4 个没搜到公开模型
  （Rainbow Dash / Starlight Glimmer / Discord / Sunset Shimmer），
  地狱客栈 15 个里缺 8 个。**这些不是"功能没做"，是 HF 上真没有**；
  另外几个作品（小马宝莉、地狱客栈）的模型多为**合集仓库**，
  「装全部」一次会下几百 MB 到几个 GB（按钮上会先写清楚再让你确认）。

## 目录

- `server.py` — 零依赖 HTTP 服务（标准库），端口 8756
- `studio.py` — 全部业务：拆解流水线、角色库、训练、体检、合成、混音、市场模型安装
- `modelhub.py` — **声音市场**：搜 HF 上公开的音色模型、挑文件、下载、清洗角色名
- `stages/` — 各阶段 CLI（UVR5 / ASR / 特征 / 分离 / 训练 / 批量合成 / 混音 / `music_src` 音乐源
  / `qc_cli.py` 成品客观质检 / `pitch_cli.py` 音高估计 / `rvc_pretrain_check.py` 底模体检
  / `dl_cli.py` 带进度的原子下载 / `sep_eval.py` 分离质量尺子 / `rvc_ckpt_check.py` 权重能不能加载）
- `web/` — 前端（原生 JS，无依赖；`mkt.js` 是声音市场那一块）
- `data/modelhub/` — 市场下载的模型原始包（按仓库分目录，重复装不会重下）
- `data/sep_pick_stats.json` — 分离选优的**跨歌**统计（哪个模型平均分高，下次先试）
- `data/roles/<id>/` — 每个角色：`slices` 切片、`final` 成品、角色 JSON
- `data/music/` — 从在线曲库下载的歌；索引在 `data/music_library.json`
- 说话权重在整合包 `GPT_weights_v5turbo/`，歌声模型在 RVC `assets/weights/`
